## 0. 한 줄 요약

개발 AI 가 아키텍처를 무시한 것이 아니다. **아키텍처를 표현할 출구가 파이프라인에
없었다.** `create_script` 는 파일을 **하나만** 돌려주게 계약돼 있었고, 클래스 이름은
**문서 번호(`spec-001`)에서 기계적으로** 만들어졌으며, 게임 오브젝트를 조립하는
(프리팹·컴포넌트 부착) MCP 도구는 **하나도 없었다.** 그래서 spec 한 장이 파일 한 개가
되는 것은 모델의 실수가 아니라 **설계된 대로의 동작**이었다.

## STEP 1 — 무슨 일이 벌어지고 있었나

### 1.2 결과물 — 눈으로 확인한 사실

표본: `git_output/work/gacha-pet-dungeon-roguelike-001` (**QA PASS 로 배포된** 결과물).

| 항목 | 실제 값 |
|---|---|
| C# 파일 | `Spec001.cs` ~ `Spec006.cs` (6개) |
| 최상위 클래스명 | `public sealed class Spec001 : MonoBehaviour` … `Spec006` |
| 프리팹(`.prefab`) | **0개** |
| 씬 `Main.unity` | 전체 170줄. GameObject **1개**(`Bootstrap`), 스크립트 **1개**만 부착 |
| 생성된 그림 | `Assets/Generated/spec-001_icon.png` 등 9장 |
| 그림을 참조하는 코드 | **0줄** |

씬에 붙은 하나는 `Spec006` 이다(guid 대조). **나머지 5개 스크립트는 게임 안 어디에도
붙어 있지 않다.** 그런데 게임은 돌았다 — `Spec006.cs` 에 답이 있다.

```csharp
private void Awake()
{
    EnsureManager<Spec001>();   // …Spec004 까지
}

private T EnsureManager<T>() where T : MonoBehaviour
{
    T manager = GetComponentInChildren<T>();
    if (manager == null)
    {
        GameObject managerObject = new GameObject(typeof(T).Name); // ← 런타임에 만든다
        managerObject.transform.SetParent(transform);
        manager = managerObject.AddComponent<T>();
    }
    return manager;
}
```

**이것이 가장 중요한 증거다.** 원래 Unity 에서는 사람이 에디터에서 오브젝트를 만들고
스크립트를 끌어다 붙인다. 그 "붙이는" 도구가 파이프라인에 없어서 모델이 **어쩔 수 없이
코드로 대신했다.** 게임이 켜지는 순간 빈 상자를 만들어 스크립트를 하나씩 꽂는다.

> **12살에게 설명하면:** 레고 설명서(spec)는 6장인데 조립할 손이 없어서, 설명서를 그대로
> 베껴 쓴 종이 6장만 나왔다. 6번째 종이에 "나머지 5장을 알아서 펼쳐라"라고 적어 뒀다.
> 완성된 레고는 없다.

부작용도 이미 보였다. `Spec005`(안에 `InventoryManager`)는 `EnsureManager` 목록에 **없다** —
만들어지긴 했지만 **아무도 실행하지 않는 죽은 코드**다.

### 1.3 이름은 어디서 오는가

`unity/codegen.py::_sanitize_class_name` 이 하는 일은 이것뿐이었다:

```python
parts = re.split(r"[^0-9A-Za-z]+", feature_id)   # "spec-001" → ["spec", "001"]
name = "".join(part[:1].upper() + part[1:] for part in parts if part)  # → "Spec001"
```

**클래스 이름이 게임 개념이 아니라 문서 번호에서 나온다.** 그리고 이 규칙은 한 번 더
못 박혀 있었다 — `.claude/skills/unity-codegen/SKILL.md` 의 예시 코드도
`public sealed class Spec003 : MonoBehaviour` 였다. 즉 **경로 A(오케스트레이터)와
경로 B(Claude Code)가 서로 다른 방식으로 같은 잘못을 강제했다.**

지금 이 함수는 **설계안이 없을 때만 도는 최후 수단**이다(§3.2 2단계).

## STEP 2 — 왜 아무도 못 잡았나

### 2.1 이걸 잡았어야 할 검사기 4개가 모두 못 잡는다

| 검사기 | 실제로 보는 것 | 왜 못 잡나 |
|---|---|---|
| `verify_contract.py` | MCP 도구 **목록**이 §03 과 맞는지 | 산출물 모양은 안 본다 |
| `qa.verify_prototype_structure` | `core_mechanics` 가 빌드에 다 들어갔는지 (LLM 판정) | 이름이 "structure" 지만 `judge.py` 의 지시문은 `missing` 을 **core_mechanics 기준**으로만 채우게 한다. 씬 계층·프리팹·컴포넌트 부착은 **판정 대상이 아니다** |
| `evals/codegen.jsonl` | 파일 하나 안에 특정 단어가 있는지 | 파일 **개수·이름·분리**는 안 잰다 |
| `spec_rules.json` S1~S6 | spec 문서의 형식과 ARCH 인용 | 코드는 안 본다 |

**그래서 "6개 파일 전부 문서 번호 이름, 5개는 아무 데도 안 붙음" 상태가 PASS 로 통과해
태그까지 붙었다.** 이것이 진짜 위험이다 — 잘못된 구조가 나오는 것보다 **잘못된 구조가
합격으로 기록되는 것**이 더 나쁘다.

### 2.2 명세 위반이다 (의견이 아니다)

`04_Prompt_Specification.md` 의 "Unity AI" 절은 **`Folder Rule`·`Prefab Rule`·
`Assembly Rule`** 을 "반드시 준수"로 못 박아 놓았다(51·53·55행). 그런데 당시 `Src/` 전체에서
`prefab` 문자열은 **0건**이었고 `codegen.py` 의 `SYSTEM_PROMPT` 에 있는 것은 Namespace
규칙뿐이었다. **명세에 있는 규칙 3개가 구현에 한 줄도 없었다.**

같이 확인된 것들:

- **에셋도 같은 병.** 그림 이름조차 문서 번호(`spec-001_icon.png`)다. `assetId` 가 같은
  종류를 덮어쓰는 결함과 **뿌리가 같다** — 식별자를 도메인 개념이 아니라 문서 번호로 잡았다.
- **1회성이 아니다.** `Lightless Deck` 에서도 똑같이 재현됐다(`Spec001~007.cs`).
- **`project_context` 에 코드 규약이 없었다.** 주석은 "청사진 요약과 **코드 규약**"이라고
  설명하는데 `build_project_context()` 가 만드는 것은 장르·아트·플랫폼·메커닉·월드구조뿐이었다.
- **1:1 인덱스 가정이 재시도 로직에 박혀 있었다.** `previous[index]` 로 이전 결과를
  재사용하고 `error_correction` 이 파일명을 `created_files` 와 대조해 귀속을 정한다.
  **파일을 N개로 늘리면 재시도 절약·에러 귀속·추적이 동시에 깨진다** — 고칠 때 반드시 함께
  옮겨야 했다(§3.2 2단계 4번).

## STEP 3 — 계획과 그 결과

### 3.1 결정 — 개발 AI 가 클래스 분해와 조립을 설계한다 (확정, 2026-07-30)

사람이 정했다. **책임을 이렇게 나눈다.**

| | 전략 AI (기획) | 개발 AI (구현) |
|---|---|---|
| 정하는 것 | **기능 경계**. "이 메커니즘은 어떤 일들을 해야 하는가" | **코드 경계**. "그 일들을 어떤 클래스·파일·프리팹으로 나누는가" |
| 산출 | spec 의 `unityHints.components` = 기능 덩어리 목록 (예: "청크 좌표 계산", "타일 생성") | 설계안 = 파일·타입·프리팹·씬 구성 (예: `World/ChunkLoader.cs`) |
| 안 하는 것 | C# 클래스 이름을 짓지 않는다. Unity 구조를 책임지지 않는다 | 기능 범위를 늘리거나 줄이지 않는다 |

> **12살에게:** 기획은 "이 요리에는 썰기·볶기·간하기가 필요하다"까지만 적는다. 그걸 도마 몇
> 개, 프라이팬 몇 개로 할지는 요리사가 정한다.

**사람 승인 게이트는 두지 않는다**(이것도 사람이 정했다). 설계안은 승인 없이 구현으로
넘어가되 **반드시 기록된다.**

**알려진 약점은 재현성 하락** — 같은 spec 이 실행마다 다르게 쪼개질 수 있다. 셋으로 막는다.

1. **설계안을 한 번만 뽑고 재사용한다.** `state` 와 `pipeline_traces` 에 적재해, 같은 실행
   안의 재시도는 설계를 **다시 뽑지 않는다.**
2. **검사를 목록 대조가 아니라 규칙 기반으로.** "설계안과 결과가 같은가"가 아니라 "결과가
   규칙을 지키는가"를 본다.
3. **빠뜨림은 기계적으로 잡는다.** 모든 `feature_id` 가 설계안의 파일 최소 한 개에 매핑돼야
   한다. 안 되면 설계안 자체를 거부한다.

**덤으로 풀린 것 셋**: (a) 설계안이 먼저 있으면 **첫 파일부터 게임 전체의 타입 지도를 본다**
(종전 `existing_types` 는 "지금까지" 만들어진 것이라 첫 파일은 형제가 없었다).
(b) 재시도가 `previous[index]` 대신 **파일 경로**로 이전 결과를 찾아 1:1 가정의 대체물이
생긴다. (c) 「모든 MonoBehaviour 는 프리팹이나 씬에 반드시 등장」을 설계 검증에 넣으면
**어디에도 안 붙은 스크립트가 설계 시점에 거부된다** — 검사가 잡는 게 아니라 애초에 안 만들어진다.

### 3.2 단계별 계획 — 0~4단계 전부 구현 완료 (2026-07-31)

| 단계 | 한 일 | 구현 위치 |
|---|---|---|
| **0. 검사부터 만든다** | 고치기 전에 "지금 상태가 FAIL 로 나오는" 검사를 먼저. 문서 번호 이름(L1)·미부착 MonoBehaviour(L2)·런타임 조립(L3)·미참조 스프라이트(L5)·어셈블리 순환(L7). `.cs.meta` guid ↔ `.unity`/`.prefab` 의 `m_Script` 대조라 **Unity Editor 없이 CI 에서 돈다** | `verify_project_layout.py`, `project_layout.py`, `unity.inspect_project_layout` |
| **1. 설계 패스** | 코드를 쓰기 전에 게임 전체 구조를 한 번에 정한다. `design_architecture(gameId, gameDesign, featurePrompts, design?) → {files[], prefabs[], scene, notes[], typeMap}`. **게임당 한 번**이라 이후 `create_script` 호출의 캐시 접두사로 쓴다 | `unity/architecture.py`, `unity.design_architecture` |
| **2. 루프 단위를 feature → 파일로** | `codegen_node` 가 `feature_prompts` 가 아니라 **설계안의 `files[]`** 를 순회한다. `create_script` 에 `plannedPath`/`plannedClass` 옵션 추가 — **문서 번호 이름이 나올 경로가 사라졌다.** `previous[index]` 를 `path → 이전 결과` 사전으로 교체 | `app/graph/nodes/codegen.py`, `unity/server.py` |
| **3. 조립 도구** | `create_prefab` → `compose_scene` → `bind_reference`. **설계안을 실행만 하고 새로 판단하지 않는다** — `prefabs[]` 가 `create_prefab` 의 인자, `scene` 이 `compose_scene` 의 인자다. 그래서 조립이 실행마다 흔들리지 않는다 | `unity/assembly.py`, `tests/test_unity_assembly.py` |
| **4. 어셈블리 분리** | 카테고리마다 `.asmdef` 를 놓아 재컴파일 범위를 줄인다. **순환을 검출해 거부하는 게 아니라 애초에 만들지 않는다** — 못 떼는 카테고리는 `skipped[]` 에 이유와 함께 남고 `Assembly-CSharp` 에 그대로 둔다. 덜 나뉜 상태는 느릴 뿐 깨지지 않는다 | `unity/assemblies.py`, `unity.define_assemblies` |

**설계안 검증 규칙 (1단계의 알맹이 — 생성이든 `design` 인자로 넘겼든 똑같이 적용)**

| 규칙 | 왜 |
|---|---|
| 모든 `feature_id` 가 최소 한 파일에 매핑 | 기획이 요구한 기능을 빠뜨리지 못하게 |
| `className` 이 `^Spec\d+$` 이면 거부 | 문서 번호 이름 재발 방지 |
| `path` 는 `Assets/Scripts/{Category}/{ClassName}.cs` | 04 명세의 **Folder Rule** 이행 |
| `dependsOn` 에 순환 없음 | 생성 순서를 정할 수 있어야 한다 |
| **모든 `MonoBehaviour` 가 `prefabs` 나 `scene` 중 한 곳에 등장** | 어디에도 안 붙은 스크립트를 **설계 시점에** 막는다 |
| 같은 `path` 중복 없음 | 나중 파일이 앞 파일을 덮어쓰는 사고 방지 |

**구현하며 계획을 한 번 줄였다.** 원래는 `create_script` 반환을 파일 N개로 넓히려 했으나,
설계안이 **이미 파일 목록을 갖고 있으므로** 파일마다 한 번씩 부르면 된다. §03 의 `{file}`
단수 반환을 그대로 두고도 spec 하나가 파일 여럿이 된다 — 계약을 덜 건드리는 쪽을 택했다.

**실물 검증에서 확인된 함정 둘.** (a) 조립 도구는 `_call_unity` 대신 `_run_command` 를 쓴다 —
경고만 있어도 `errorCode 4000` 이 오는데 그 안에 성공 결과가 들어 있는 경우가 있어서,
**우리 결과 JSON 을 먼저 찾고** 없을 때만 Unity 의 실패 신호를 따른다. (b) `compose_scene`
이 씬을 `EditorBuildSettings` 에 등록한다 — 활성 씬이 없으면 `build_project` 가 그 자리에서
실패한다. (c) `.asmdef` 를 놓는 순간 `Assembly-CSharp` 가 자동 참조하던 패키지 어셈블리가
사라진다 — `assemblies.py` 가 소스의 `using` 을 읽어 참조를 싣는 것이 장식이 아니다.

### 3.4 하지 말아야 할 것

- **프롬프트만 고치고 끝내기.** 모델은 이미 저항했다 — 한 파일에 클래스 3개를 밀어 넣고,
  없는 조립 도구를 런타임 `AddComponent` 로 흉내 냈다. **말이 부족한 게 아니라 출구가 없었다.**
- **한쪽 경로만 고치기.** `unity/codegen.py` 만 고치면 경로 B 는 여전히 `Spec003` 을 만든다.
- **전략 AI 에게 C# 클래스 이름을 짓게 하기.** §3.1 로 그건 개발 AI 의 몫이 됐다. spec 에
  `PlayerController` 같은 타입명이 다시 등장하면 경계가 무너진 것이다
  (검사: `11_역할경계_계약서.md` 의 S8).
- **설계 패스를 재시도마다 다시 부르기.** §3.1 재현성 대비책 1번이 무너진다. **게임당 한 번**이다.
- **`Src/DeveloperAI/app/graph/` 를 임의로 수정하기.** `CLAUDE.md` 가 금지한다.
- **기존 게임을 손으로 고쳐 "해결됐다"고 하기.** 그 게임은 **표본**이다. 파이프라인을 고친 뒤
  **같은 청사진으로 다시 돌려서** 비교해야 고쳐진 것이다 (남은 작업 — 백로그 참고).
