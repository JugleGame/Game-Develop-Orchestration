## 1. 배포 저장소에 게임 파일이 들어가지 않음 — ✅ 해결

### 1.1 현상 (원래 증상)

`deployment.py` 의 호출 순서를 그대로 돌리면 여섯 호출이 **전부 성공을 반환하고**
유효한 40자리 SHA-1 과 태그까지 발급됐다. 그런데 발행된 bare 저장소를 독립적으로
클론해 보면:

```
published commit : 07d81e6e   (오케스트레이터에 보고된 해시와 일치)
TRACKED FILES    : 없음 — 저장소가 비어 있음
tags             : ['v0']
```

이 값이 `GET /games/{id}/artifact` 로 그대로 노출된다. **사용자는 정상 배포로
인지하지만 저장소에는 아무것도 없다.** 파이프라인이 끝까지 성공을 보고하면서
산출물이 존재하지 않는 상태 — 이것이 이 문서에서 가장 심각한 항목이었다.

**원인**: §03 GitMcpServer 도구 7종 중 **파일 경로나 내용을 인자로 받는 도구가 하나도
없었다.** GitMcpServer 의 작업 클론(`GIT_ROOT/work/{repoName}`)과 Unity 프로젝트 실물은
다른 위치인데 둘을 잇는 수단이 계약에 없었다. `git_commit` 은 언제나 비어 있는 자기
클론을 스테이징할 뿐이었다.

같은 뿌리의 두 번째 증상: QA 의 `build` 인자도 빌드 메타데이터뿐이라 **QA 가 실제 코드나
실행 가능한 빌드를 보지 못했다.** 서버 간 산출물 공유 위치가 정의돼 있지 않다는 하나의
공백이 두 곳에서 터진 것이다.

### 1.5 해결 — `git_commit(sourcePath?)`

`sourcePath` 가 주어지면 그 디렉터리를 작업 클론에 **미러링한 뒤** 커밋한다.
(환경변수 `GIT_SOURCE_PATH` 폴백도 있으나 정식 경로는 인자다.)

동기화 규칙:

- **미러링이다** — 프로젝트에서 지운 파일은 저장소에서도 지워진다. 단순 복사면 삭제된
  스크립트가 발행 이력에 영원히 남는다.
- **Unity 재생성물 제외** — `Library/` `Temp/` `Obj/` `Build(s)/` `Logs/`
  `UserSettings/` `MemoryCaptures/` `.vs/` `.idea/`, `*.csproj` `*.sln` `*.user`.
  제외하지 않으면 게임보다 큰 머신 로컬 캐시가 발행된다.
- **발행 저장소에 같은 규칙의 `.gitignore` 를 넣는다** — 사람이 클론해 캐시를 다시
  커밋하지 않도록.
- 변경 판정은 크기+mtime. 배포마다 전체 해시는 커밋보다 비싸다.

검증(§1.1 과 완전히 같은 호출에 `sourcePath` 하나만 추가): `TRACKED FILES: 없음` 자리에
실물 6개가 들어갔고 163,840바이트 캐시는 빠졌다(체크아웃 585 bytes).

**소스가 지정되지 않으면 빈 커밋 WARNING 이 남아 관측 가능하다:**

```
WARNING GitMcpServer.repo Commit contains no files; nothing was staged into the working clone
```

### 1.6 배선 상태 — 전부 완료

- **§03**: `git_commit` 에 `sourcePath?` 정식 등재 ✅
- **UnityMcpServer**: `build_project` 가 `projectPath`(= `UNITY_PROJECT_PATH`)를 반환한다 ✅
  — 배포 대상은 빌드 바이너리가 아니라 **소스**이므로 이 값이 필요했다.
- **오케스트레이터**: `deployment.py` 가 `build_result["projectPath"]` 를 `source_path` 로
  넘긴다 ✅

## 2. `git_*` 5종이 대상 저장소를 식별할 수 없음 — ✅ 해결

**원래 문제**: `repoName` 을 받는 도구가 `git_init` 하나뿐이었다. 동시에 §03 §2 는
**호출 1건당 세션 1개**를 규정하므로 세션 상태로 저장소 정체성을 이어받을 수도 없다.
즉 "게임 1개 = 저장소 1개" 전략과 "도구가 저장소를 지목할 수 없다"는 계약이 모순이었다.

**해결**: §03 의 `git_*` 6종에 `repoName?` 을 등재하고, 오케스트레이터가
`state["repo_name"]` 을 **매 호출에 싣는다**(`git_client.py::_with_repo`).

옵션으로 둔 것은 하위 호환 때문이다. 생략하면 "가장 최근 `git_init` 저장소"로 폴백하는데,
그 폴백은 `MAX_CONCURRENT_JOBS=1` 에서만 정확하다 — **동시 Job 이 2개가 되는 순간 서로의
저장소에 커밋할 수 있다.** 그래서 오케스트레이터는 폴백에 의존하지 않는다.

## 3. Asset 도구에 `gameId` 가 전달되지 않음 — ✅ 해결

### 3.2 영향 (실측)

`gameId` 가 없으면 서버가 `"default"` 로 폴백한다. 판타지 게임과 SF 게임을 순서대로
생성한 실측 결과:

```
게임A(판타지) f-1: assetId='default__f-1__character'  seed=1405615973467191904
게임B(SF)     f-1: assetId='default__f-1__character'  seed=1405615973467191904  ← 동일

두 게임의 assetId 교집합 : ['default__f-1__character', 'default__f-2__tile']
전체 styleSeed 종류 수    : 1   (게임별로 달라야 하므로 2여야 정상)
매니페스트                : manifests/default.json 하나, 등록 자산 2개 (4여야 정상)
```

**게임A 의 레코드가 사라진다. 파일명도 같으므로 디스크의 PNG 까지 덮어써진다.**
정리하면 (a) 게임별 아트 스타일 고정이 완전히 무력화되고, (b) 먼저 만든 게임의 자산이
매니페스트·PNG 양쪽에서 유실되고, (c) 검수 매니페스트가 합쳐져 게임별 상태를 구분할 수
없다. **동시 실행이 아니어도 발생한다** — 순차로 두 개 만들면 두 번째가 첫 번째를 지운다.

**해결**: `asset_client.py` 의 세 메서드가 `gameId` 를 싣고(`_payload`), §03 Asset 표에도
`gameId?` 를 등재했다.

## 4. Asset 서버 도구가 호출되지 않음 — ◐ 생성 2종 해결, 검수 2종 남음

### 4.2 원래 제안

- 생성 2종(`generate_ui_asset`/`generate_3d_placeholder`): feature 성격에 따라 분기 → §4.4 로 해결
- 검수 4종: Asset 서버는 자산을 `pending` 으로 기록하지만 **파이프라인은 승인을 기다리지
  않는다.** 검수를 배포 게이트로 삼으려면 `asset_review_summary` 의 `readyForBuild` 를
  Deployment 진입 조건에 넣어야 한다 → `AssetReview` 노드로 결론이 났다.

### 4.4 `generate_ui_asset` / `generate_3d_placeholder` 배선 — ✅ 해결됨 (2026-07-29)

**막혀 있던 것은 분기 로직이 아니라 신호였다.** `FeatureImplementationPrompt`(§5.2)에
자산 종류를 알 수 있는 필드가 없었다. spec 의 `unityHints.assetsNeeded` 는
`_to_feature_prompt()` 가 `- 필요 에셋: A, B` 라는 **문장으로만** 렌더링해 넘겼고,
오케스트레이터에게는 긴 마크다운의 한 줄일 뿐이었다.

그래서 §5.2 에 **선택 필드 하나를 더했다** (기본값 빈 배열이라 안 채우는 기획자는
이전과 똑같이 동작한다):

```json
"assets_needed": ["string"]        // unityHints.assetsNeeded 를 그대로
```

**왜 항목 단위여야 하나 — 실측.** 종전에는 `description` **전체**를 프롬프트로
`generate_2d_sprite` 에 넘겼다. `asset/render.py::classify()` 는 **처음 걸린 키워드**로
종류를 정하고 표의 순서가 UI 를 먼저 본다(`ui_button` → `ui_panel` → `icon` → `tile` →
`character` → `prop`). 그래서 합격 기준에 "재시작 **버튼**을 누르면…" 한 줄이 있는
플랫포머 spec 이 **버튼 스프라이트 한 장**만 받고 플레이어 스프라이트는 아예 안 만들어졌다.
자산을 이름 단위로 쪼개면 이 문제가 원인에서 사라진다.

**분기 규칙** (`app/graph/nodes/assetgen.py::select_asset_tool`):

| 항목에 들어 있는 말 | 도구 |
|---|---|
| `3d` `3-d` `mesh` `메시` `메쉬` `입체` | `generate_3d_placeholder` |
| `ui` `hud` `button` `panel` `menu` `dialog` `inventory` `icon` `cursor` `badge` `버튼` `패널` `메뉴` `아이콘` `인벤토리` `커서` `대화창` | `generate_ui_asset` |
| 그 외 | `generate_2d_sprite` |

3D 를 먼저 본다 — "3D 인벤토리 아이콘"은 UI 를 언급하는 3D 요청이다. LLM 을 쓰지 않는
이유는 이 판단이 자산마다 돌고 **같은 기획이 매번 같은 결과를 내야** 하기 때문이다.

**이 목록이 서버의 `_KIND_KEYWORDS` 와 갈라져도 조용히 깨지지 않는다.** 오케스트레이터는
"UI 인가"만 답하고 버튼/패널/아이콘은 서버가 다시 고른다. 어긋나도 양쪽 모두 UI 로
수렴한다.

**남은 것**: `list_pending_assets` / `review_asset` 은 여전히 미호출이다. 승인 UI 가 없고,
반려된 자산이 있으면 배포 전에 사람에게 넘긴다.

## 5. 기획서의 `art_style` 이 Asset 서버까지 도달하지 못함 — ✅ 해결

**원래 문제**: Asset 도구 3종이 `featureId`·`prompt` 만 받아 `art_style` 을 받을 인자가
없었다. 서버는 `ASSET_ART_STYLE` 기본값 `"pixel art"` 를 썼다. `art_style` 은 §02 §5.1
`GameDesignDocument` 의 정식 필드인데 **소비자에게 가는 경로가 설계에서 빠져 있었다.**

### 5.2 순서 의존성 (실측)

스타일은 **최초 `generate_*` 호출 시점에 고정**되고 이후 변경이 무시된다 — 반쯤 만든
게임이 도중에 다시 칠해지지 않게 하는 **의도된 잠금**이다.

```
최초 generate_*로 고정된 artStyle : 'pixel art'
이후 'dark fantasy'로 요청한 결과 : 'pixel art'
팔레트가 바뀌었는가              : False
```

그래서 순서가 중요하다: `establish_art_style` 은 **반드시 첫 `generate_*` 보다 앞**이어야
한다. 그러지 않으면 모든 게임이 환경변수 기본값으로 영구 고정된다.

**해결**: Asset 도구에 `artStyle?` 옵션 인자를 두고 §03 에 등재했으며,
`asset_client.py` 가 `art_style` 을 함께 보낸다.

### 5.4 남은 판단 — 아트 일관성 사양이 문서에 없다

`Doc/` 전체에서 아트 관련 규정은 `art_style` 문자열 필드와 §2.5 의 "프로시저럴 도형으로
대체 후 고도화"뿐이다. **분위기·컨셉 일관성 요구사항은 문서화돼 있지 않다.**
`asset/style.py` 는 이를 전제하고 게임별 팔레트 고정을 구현했으나 문서 근거가 없다 —
요구사항으로 유지할지 정해 §02 나 §03 에 명시하는 편이 좋다.

## 7. 참고 — 계약 변경 없이 서버에서 고친 것

- **GitMcpServer 태그 push 거부 은폐**: GitPython 은 push 거부 시 예외를 던지지 않고
  `PushInfo` 플래그(`flags=1032`, `[rejected]`)로만 알린다. 모든 push 에서
  `PushInfo.ERROR` 를 검사하고, 태그는 `ls-remote` 로 원격을 먼저 조회해 충돌을 판정한다.
- **QaMcpServer LLM 출력 타입 검증**: `line: 3.7`, `file: 123` 같은 값을 통과시키면
  오케스트레이터 Pydantic 에서 **처리되지 않은 `ValidationError` 로 터지며 §03 에러코드
  체계를 우회한다.** 이제 서버에서 5000 으로 거부한다.
- **QaMcpServer 타임아웃 역전**: anthropic SDK 기본 read timeout 600초가 §03 §5 의 QA
  예산 180초를 초과했다. 서버가 먼저 실패하도록 150초로 명시.
- **AssetGen — 검수가 Unity 임포트 경로를 끊던 문제**: `review_asset` 이 파일을
  `approved/`·`rejected/` 로 **이동**시켜 승인·반려 양쪽 모두 Unity 참조가 끊어졌다.
  경로를 `assets/{gameId}/` 로 고정하고 검수 결과는 매니페스트에만 기록한다.
- **로깅 함정**: `extra` 에 `LogRecord` 예약 키(`created` `message` `filename` `module`
  `lineno` `process` `args` `name` `levelname` `asctime`)를 쓰면 `KeyError` 로 **도구
  전체가 실패한다.** API 키와 프롬프트 본문은 기록하지 않는다.

## 8. UnityMcpServer 도구 5종 추가 — ✅ 반영됨 (2026-07-31)

§03 `UnityMcpServer` 도구표에 다섯을 더했다. **기존 여섯은 인자도 반환도 바뀌지 않았다** —
계약을 넓히기만 했으므로 기존 호출자는 그대로 동작한다.

| 새 도구 | 왜 필요했나 |
|---|---|
| `design_architecture` | 클래스 이름이 게임 개념이 아니라 문서 번호(`spec-001` → `Spec001`)에서 나왔다. 이름·폴더·분해를 **코드를 쓰기 전에** 정하는 자리가 없어서다 |
| `create_prefab` | 04 명세의 **Prefab Rule** 을 이행할 도구가 없었다 (`Src/` 전체에 `prefab` 0건) |
| `compose_scene` | 「씬 구성」의 실제 도구가 빈 씬을 만드는 `create_scene` 뿐이었다 |
| `bind_reference` | `import_asset` 은 임포트만 하고 참조를 꽂지 않는다. 그림 9장을 만들고 참조하는 코드가 0줄이었다 |
| `inspect_project_layout` | QA 에 가는 `build` 문자열로는 "이 스크립트가 어디에 붙어 있는가"를 알 수 없었다 |

전부 같은 뿌리다 — **아키텍처를 표현할 출구가 파이프라인에 없었다**
(진단: `06_코드생성_아키텍처_진단_260730.md`).

### 8.2 계약을 넓히지 **않은** 곳 — `create_script`

원래는 반환을 `{files[], primary}` 로 넓히려 했으나 취소했다. `design_architecture` 가
이미 파일 목록을 갖고 있어 **파일마다 한 번씩 부르면** 되므로, `{file}` 단수 반환을 그대로
두고도 spec 하나가 파일 여럿이 된다. 대신 옵션 인자만 더했다(`plannedPath`/`plannedClass`/
`projectContext`/`existingTypes`/`previousSource`/`contents`). 필수는 여전히
`featureId`·`prompt` 둘뿐이다.

### 8.3 `verify_contract.py` 는 어디까지 보는가

**필수 인자 이름만** 대조한다. 옵션 인자는 자유롭게 늘릴 수 있고 계약 초과 도구
(`unity_bridge_status`)는 의도적으로 무시된다.

**못 보는 것**: 도구가 실제로 도는지는 보지 않는다. `build_project` 가 클래스명 하나 때문에
한 번도 동작하지 않았는데도 이 검사기는 계속 통과했다. 조립 3종은 그 실패가 반복되지 않도록
**소스 텍스트 계약**(`internal class CommandScript : IRunCommand`, 진입점 시그니처, 정적
차단 토큰 부재, `global::` 한정)을 `tests/test_unity_assembly.py` 가 별도로 고정한다.

### 8.4 키 없이 쓰는 인자 (경로 B)

`design_architecture` 는 LLM 을 쓰므로 `design` 인자에 완성된 설계안을 넘기면 모델을 부르지
않고 **검증만** 한다. 넘긴 값도 생성한 값과 똑같이 거부 규칙을 통과해야 하므로 이 우회가
스키마 보장에 구멍을 내지 않는다. 조립 3종은 LLM 을 안 써서 이런 인자가 없다.

## 9. UnityMcpServer 에 `define_assemblies` 추가 — ✅ 반영됨 (2026-07-31)

06 문서 §3.2 의 **4단계(어셈블리 분리)** 를 이행한다. `unity` 는 이제 13개다
(계약 12 + 진단용 `unity_bridge_status`).

| 도구 | 인자 |
|---|---|
| `define_assemblies` | `gameId: str, projectPath?: str, apply?: bool` |

생성된 C# 이 전부 `Assembly-CSharp` 한 덩어리라 파일 하나를 고쳐도 프로젝트 전체가
재컴파일됐다. 04 명세의 **Assembly Rule** 을 이행할 도구가 없었다.

- **LLM 을 쓰지 않는다.** `git` 과 같다 — 판단이 아니라 계산이다. 그래서 두-경로 우회 인자도
  `usage` 도 없다.
- **설계안(`dependsOn`)이 아니라 소스를 읽는다.** 설계안은 의도이고 컴파일되는 것은 실제로
  쓰인 타입이다. 참조를 하나라도 빠뜨리면 컴파일이 깨지므로 결과를 봐야 한다.
- **`apply=false` 로 계획만 받을 수 있다.** `.asmdef` 를 놓는 것은 컴파일 단위를 바꾸는
  일이고, 잘못되면 증상이 "느려진다"가 아니라 **"컴파일이 아예 안 된다"** 이다.
- **`skipped[]` 를 반환한다.** 떼어내지 못한 카테고리가 **이유와 함께** 나와야 왜 안
  빨라졌는지 안다. 조용히 빠지면 그 자리에서 진단이 끊긴다.
